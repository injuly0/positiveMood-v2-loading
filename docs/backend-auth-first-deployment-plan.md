# 邀请认证优先部署与分阶段执行计划

> 状态：已确认，作为后端第一轮实施、服务器实验和后续分阶段交付顺序。  
> 关联总规范：`backend-data-analytics-mvp-spec.md`。  
> 本文只规定实施分布和每阶段验收，不取代总规范的数据表、隐私和埋点口径。

## 1. 第一轮目标

第一轮不是只完成一个孤立的“生成邀请码接口”，而是完成并部署最小认证闭环：

```text
SSH 生成邀请码
  → 用户邀请码激活
  → 设置用户名和密码
  → 建立登录会话
  → 刷新后保持登录
  → 退出登录
  → 再用用户名和密码登录
```

完成该闭环可以一次验证：

- FastAPI 和 SQLite 能否在 2 核 2G 服务器稳定运行；
- Alembic 迁移能否安全执行；
- Nginx `/api/` 反向代理和 `/letter/` 静态前端能否共存；
- HTTPS 安全 Cookie 能否正常建立、携带和撤销；
- 进程与服务器重启后账号和会话数据是否仍然存在；
- 邀请码一次性使用、用户名唯一和密码哈希是否正确。

第一轮不实现馆藏上云、埋点、真实 Qwen、管理后台或前端大规模视觉改造。

## 2. 首页最小改动

### 2.1 固定内测说明

首页增加：

```text
当前为邀请内测，首次使用需凭邀请码激活
邀请码请前往小红书 @xxx 获取
```

并提供：

```text
已有账号？登录
```

实施前将 `@xxx` 替换为真实小红书账号。文案强调“首次激活”，不能写成“每次凭邀请码登录”。

### 2.2 保留现有首页场景

不修改：

- 三张首页场景背景；
- 默认、写信聚焦、馆藏聚焦三种状态；
- 首页标题和原有视觉转场；
- 两个透明热区的位置与 hover/focus 效果；
- `/letter/` 部署路径。

只新增：

- 启动时的认证状态检查；
- 低干扰内测说明；
- 邀请激活表单；
- 已有账号登录表单；
- 认证检查中的不可交互状态；
- 登录成功后恢复原热区行为。

### 2.3 首页状态

```text
auth_checking   正在调用 GET /api/v1/auth/me，两个热区暂不可导航
auth_error      无法确认登录状态，显示重试；不能直接降级为 anonymous
anonymous       可浏览首页；点击任一核心热区打开认证层
authenticated   两个热区沿用现有转场和导航
```

认证浮层至少有两种模式：

```text
activate  邀请码 + 新用户名 + 新密码 + 确认密码
login     用户名 + 密码
```

邀请码激活成功后直接建立登录会话，不要求用户再次输入用户名和密码。

### 2.4 守卫边界

首页热区拦截不是安全边界。还必须同时实现：

- 未登录直接访问 `/letter/record` 时返回首页并打开认证入口；
- 未登录直接访问 `/letter/question-selection`、`/letter/question-answer`、`/letter/today-collection/...` 和 `/letter/display-archive` 时同样受保护；
- 后端每个私有 API 独立校验会话；
- 前端认证状态不能代替服务端权限判断；
- Cookie 认证的状态修改请求校验同源 `Origin` 并采用 CSRF token 或等效防护；
- 登录成功后可以回到用户原本尝试进入的安全内部路径；
- 不允许外部 URL 作为 `returnTo`，避免开放重定向。

## 3. 管理员认证决策

### 3.1 MVP 不建立管理员网站账号

第一版邀请码由项目所有者 SSH 登录服务器后运行管理命令生成：

```text
letter-admin create-invite
letter-admin create-password-reset --user <user-id-or-username>
letter-admin disable-user --user <user-id-or-username>
```

SSH 私钥、服务器账号权限和主机访问控制共同构成管理员认证。因此本阶段不需要在 `users` 表中增加管理员角色，也不需要管理员用户名和密码。

管理命令必须调用与 FastAPI 相同的 service/repository 层，不能复制一套邀请码生成和数据库写入逻辑。

### 3.2 何时才需要管理员账号

出现以下需求时再新增管理员认证与后台：

- 不方便 SSH 登录服务器；
- 多个人需要发放邀请码；
- 需要在浏览器中查看、撤销和批量管理邀请码；
- 需要运营角色和操作审计；
- 需要远程禁用用户或处理密码重置。

到那时再增加管理员角色、强认证和受保护的 `/api/v1/admin/...`。不能将当前管理命令直接暴露成无认证 HTTP 接口。

## 4. 分阶段执行

每个阶段必须可以独立验收；前一阶段不稳定时不进入下一阶段。

### 阶段 A：可部署后端骨架

范围：

- 建立 FastAPI 应用结构；
- 配置开发、测试、生产环境变量；
- 建立统一成功/错误响应约定；
- 提供 `GET /api/v1/health`；
- 接入结构化日志，但不记录密码、邀请码或用户正文；
- 准备 Uvicorn 单 worker 启动方式；
- 准备 systemd 服务和 Nginx `/api/` 反向代理；
- 确保 `/letter/` 现有静态部署不受影响。

验收：

- [ ] 本地和服务器均可访问 health；
- [ ] 非法请求返回统一错误而非堆栈；
- [ ] FastAPI 进程退出后 systemd 能恢复；
- [ ] 服务器重启后服务自动启动；
- [ ] `/letter/` 深层 SPA 路由仍可刷新。

### 阶段 B：SQLite、迁移与管理命令

范围：

- 接入 SQLAlchemy 和 Alembic；
- 建立 `users`、`invite_codes`、`sessions`；
- 开启 WAL、外键和 busy timeout；
- 实现共享业务层；
- 实现 `letter-admin create-invite`；
- 实现一次性密码重置码和禁用用户命令；
- 数据库文件放在发布目录之外。

验收：

- [ ] 首次迁移可以从空库创建表；
- [ ] 重复执行迁移不会破坏数据；
- [ ] 生成邀请码时同时预留确定的用户 ID；
- [ ] 数据库只保存邀请码哈希；
- [ ] 邀请码明文只在生成时输出一次；
- [ ] 程序重新发布不会覆盖数据库文件。

### 阶段 C：认证 API 闭环

范围：

```text
POST /api/v1/auth/activate
POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/auth/me
POST /api/v1/auth/reset-password
```

激活请求一次携带邀请码、用户名和密码；验证邀请码、写入账号、标记邀请码已使用、创建会话必须处于同一事务。密码使用 Argon2id，登录态使用带明确有效期的服务端会话和安全 Cookie。所有状态修改请求校验同源 `Origin` 并采用 CSRF token 或等效防护。

验收：

- [ ] 无效、过期、已使用和已撤销邀请码均不能激活；
- [ ] 有效邀请码只能成功激活一次；
- [ ] 用户名大小写不敏感唯一；
- [ ] 数据库不存在明文密码；
- [ ] 激活成功后 `/auth/me` 立即返回当前用户；
- [ ] 刷新、关闭再打开浏览器后按会话期限保持登录；
- [ ] logout 后旧 Cookie 不能继续访问私有接口；
- [ ] 跨站请求不能利用用户 Cookie 执行激活、退出、重置或其他状态修改；
- [ ] 登录失败响应不能用于枚举用户名；
- [ ] 登录、激活和重置接口有速率限制。

### 阶段 D：先部署后端并独立实验

在改首页前，将阶段 A～C 部署到真实服务器。使用命令行或临时 API 客户端测试，不先把正式首页改动混入后端排错。

实验清单：

1. SSH 生成一个邀请码；
2. 使用无效邀请码激活，确认失败；
3. 使用有效邀请码设置用户名和密码；
4. 重复使用同一邀请码，确认失败；
5. 调用 `/auth/me` 验证 Cookie；
6. 退出后确认会话失效；
7. 重新用用户名和密码登录；
8. 重启 FastAPI，确认账号仍在；
9. 重启服务器，确认 API 自动恢复；
10. 在另一浏览器登录同一账号；
11. 使用管理命令禁用用户，确认已有会话失效；
12. 生成一致性备份并在独立路径恢复验证。

阶段 D 通过以后，认证后端才进入“可供首页接入”状态。

### 阶段 E：首页认证接入

范围：

- 新增认证状态容器；
- 应用启动时调用 `/auth/me`；
- 加入内测说明、激活表单和登录表单；
- 未登录点击两个热区时打开认证层；
- 登录后恢复原始柔光转场；
- 增加受保护路由守卫；
- 退出登录后清空运行时馆藏；
- 旧的无 owner 草稿不自动归给新账号。

验收：

- [ ] 首页背景、标题、热区坐标和聚焦效果未被破坏；
- [ ] `auth_checking` 时不会闪现可进入的私有页面；
- [ ] `/auth/me` 网络失败进入可重试错误态，不被误判成退出登录；
- [ ] 未登录用户不能通过直接输入深层 URL 绕过；
- [ ] 激活成功后无需再次登录；
- [ ] 已有用户可切换到登录模式；
- [ ] 登录成功后可以继续原本想进入的应用内页面；
- [ ] 认证 token 不进入 localStorage；
- [ ] 同一浏览器切换账号不会泄漏其他用户数据。

### 阶段 F：第一轮小规模内测

只邀请少量测试用户验证：

- 邀请码获取和激活是否容易理解；
- 用户是否误以为邀请码是永久密码；
- 用户名冲突和密码错误反馈是否清晰；
- 手机和桌面首页认证层是否可操作；
- Cookie、服务器重启和会话过期是否稳定；
- 2 核 2G 的 CPU、内存、磁盘和日志增长是否正常。

这一轮测试数据可以丢弃，不迁移现有浏览器测试馆藏。

## 5. 后续阶段顺序

邀请认证通过真实服务器实验后，再按以下顺序继续：

1. `memory_entries` 与服务端馆藏编号事务；
2. 完成馆藏“创建 → 列表 → 详情”的服务端闭环；
3. 将 `ArchiveState` 改为 API 运行时缓存，Zustand Persist 只保留用户隔离草稿；
4. 接入查看、擦亮与珍藏事务；
5. 建立 `analytics_events` 和批量接收；
6. 先接少量事件验证，再补完整核心漏斗；
7. 接入真实 Qwen，并单独验证模型部署的内存与耗时；
8. 建立指标查询、备份恢复和运行监控；
9. 扩大邀请范围。

这个顺序避免同时排查认证、馆藏、埋点和模型四类问题，也避免在服务端数据源尚未稳定时提前重写整个前端 Store。

## 6. 第一轮明确不做

- 不开放管理员网页或公网邀请码生成 API；
- 不创建管理员用户角色；
- 不接 `memory_entries`；
- 不迁移当前浏览器测试馆藏；
- 不重做首页视觉和热区；
- 不接完整埋点；
- 不接真实 Qwen；
- 不做邮箱找回密码；
- 不使用多 Uvicorn worker；
- 不迁移 PostgreSQL。

## 7. 实施前需要替换的配置值

以下是配置值而不是架构问题，实施时确定即可：

- 生产域名；
- 首页小红书账号 `@xxx`；
- 邀请码默认有效期；
- 密码重置码有效期；
- 登录会话有效期；
- 数据库与备份绝对路径；
- Nginx/Caddy 选择；
- 服务器 SSH 管理命令的安装位置；
- 允许的前端 Origin 和 Cookie 策略。

## 8. 第一轮完成定义

只有同时满足以下条件，第一轮才算完成：

- [ ] A～D 后端实验全部通过；
- [ ] 首页仅增加认证相关最小改动且原视觉回归通过；
- [ ] 邀请、激活、登录、保持会话、退出和再次登录形成闭环；
- [ ] 深层路由和私有 API 无法绕过认证；
- [ ] 邀请码与密码明文没有进入数据库和日志；
- [ ] FastAPI 与服务器重启后数据和服务均可恢复；
- [ ] SQLite 备份已真实恢复验证；
- [ ] 少量真实设备完成内测流程；
- [ ] 第一轮未提前混入馆藏、埋点或 Qwen 改造。
