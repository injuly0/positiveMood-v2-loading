# Record Page Spec v5 补充：异步柔光转场

> 状态：已确认并实施  
> 适用路径：`RecordEntryPage` → `QuestionSelectionPage`  
> 基础文档：`record-page-spec-v5.md`、`柔光聚焦页面转场规范.md`

## 1. 与 Record Page Spec v5 的关系

`record-page-spec-v5.md` 继续作为记录页视觉、布局、引导问题、正文输入、自动保存和 Footer 的实现依据。

本文只补充 v5 未定义的内容：

- 点击“收藏这份记忆”后的跨路由体验；
- 本地 AI 问题生成与柔光转场的协调；
- 等待文案和时间规则；
- 记录页、转场协调器、转场视觉层和问题选择页的职责边界。

如两份文档在上述范围内存在冲突，以本文为准；记录页内部视觉布局仍以 v5 为准。

## 2. 产品决策

原先的流程是：柔光转场结束后进入问题选择页，再显示独立的“正在读这封信”加载页。连续出现两次过渡会产生重复和突兀感。

更新后的流程将加载等待合并到同一次柔光转场中：

```text
点击“收藏这份记忆”
  → 光从该按钮中心扩散
  → 柔光完全覆盖记录页
  → 在覆盖层内显示等待文案并等待问题生成
  → 三个问题准备完成
  → 切换到问题选择页
  → 柔光淡去，直接显现三个问题
```

正常流程不再出现独立的 `ThinkingLoader` 页面。

## 3. 职责边界

### 3.1 转场视觉组件

`WarmLightTransitionLayer` 负责：

- 根据本次点击控件的位置渲染光源；
- 播放覆盖、完全覆盖和揭示动画；
- 在异步转场的完全覆盖阶段显示业务传入的文案；
- 转场运行期间拦截底层指针操作。

它不读取记录草稿、不请求 AI、不判断问题内容。

### 3.2 转场协调器

路由级协调器负责：

- 计算点击控件中心和覆盖整个视口所需的光斑尺寸；
- 防止重复转场；
- 等待最短展示时间；
- 等待可选的异步 Promise；
- 在数据准备后切换路由；
- 等待目标页完成渲染，再开始揭示。

普通转场不传 Promise，只等待标准动画时间。

### 3.3 记录页业务

记录页负责：

- 校验正文非空；
- 保存最新正文；
- 只把用户正文 `recordText` 交给问题生成服务；
- 校验返回的框架和三个问题；
- AI 请求失败或返回非法结果时使用现有 fallback；
- 把框架和三个问题写入可恢复草稿。

记录页的引导主题和引导问题只用于激发书写灵感，不保存、不归档，也不发送给 AI。

### 3.4 问题选择页

问题选择页负责：

- 读取已经准备好的框架和三个问题；
- 展示单选问题列表；
- 保存用户选择并进入回答页；
- 数据不完整时守卫返回记录页。

问题选择页不再发起 AI 请求，也不承担独立加载动画。

## 4. 时间规则

### 4.1 普通柔光转场

普通转场沿用项目统一节奏：

| 时间 | 行为 |
| --- | --- |
| `0–540ms` | 从实际点击控件中心扩散并覆盖旧页面 |
| `500–540ms` | 在视觉完全遮挡附近完成路由切换 |
| `540–970ms` | 保持最大光斑尺寸并淡出 |
| 约 `1000ms` | 转场结束并解锁 |

普通转场不显示文字，不额外停留。

### 4.2 记录页到问题选择页

| 时间 | 行为 |
| --- | --- |
| `0ms` | 保存正文、发起问题生成 Promise、柔光开始覆盖 |
| `540ms` | 柔光完全覆盖，显示主等待文案 |
| `1200ms` | 达到允许揭示的最早时间 |
| `3000ms` | Promise 仍未完成时替换为延迟文案 |
| `max(1200ms, Promise 完成时间)` | 写入结果并切换到问题选择页 |
| 目标页完成一帧渲染后 | 用 `430ms` 淡出柔光 |

开始揭示的计算规则：

```text
revealStart = max(1200ms, questionPromiseResolvedAt)
```

前端不能用当前 Mock 的固定耗时推算揭示时间。

## 5. 等待文案

前 `0–3000ms`：

```text
正在读这封信，并为你寻找三个问题
```

超过 `3000ms` 且问题仍未准备完成：

```text
还在整理，可能需要一点时间
```

本阶段不增加积极心理学知识轮播、伪进度条或更多等待层级。

## 6. AI 请求适配

当前版本的 `fetchQuestionFromLLM(recordText)` 是模拟本地大模型的 Promise，包含约 `1800ms` 的 Mock 延迟。

后续将改为通过内网穿透访问真实本地模型接口。为避免届时重写页面：

- 转场协调器只等待 Promise，不感知请求地址和协议；
- 页面不读取 Mock 延迟；
- 真实接口地址、超时、取消、鉴权和响应转换属于 AI 服务层；
- 服务层输出格式继续保持 `{ frameworkId, questions }`；
- 页面边界继续校验受支持的框架以及恰好三个有效问题。

替换真实接口时，转场、记录页和问题选择页的职责不变。

## 7. 草稿与归档

本次补充不改变归档内容：

```text
原始记录 + AI 问题 + 用户回答
```

问题来源可以在未完成草稿中标记为 `ai` 或 `fallback`，只用于问题选择页提示，不进入最终 `MemoryEntry`。

回答页仍通过 `commitDraft()` 完成原子归档，流程不变。

## 8. 异常与边界

- 空正文不得启动请求或转场。
- 转场运行期间重复点击不得产生第二次请求。
- AI 返回的框架不受支持、问题不是三条或问题内容无效时，使用现有 fallback。
- Promise 完成前不得揭示空的问题选择页。
- 直接访问问题选择页但草稿数据不完整时，返回记录页。
- 动画状态、定时器和光源坐标不写入 Zustand Persist。
- `prefers-reduced-motion` 只缩短空间运动，仍需等待 Promise 和保持文案可读。

## 9. 验收标准

- [ ] 光从“收藏这份记忆”按钮中心产生，不从屏幕中心产生。
- [ ] 柔光完全覆盖后才出现等待文案。
- [ ] 问题生成完成前，问题选择页不会显露。
- [ ] 问题生成完成后，柔光淡去并直接显示三个问题。
- [ ] 正常流程中不存在第二个 `ThinkingLoader` 页面。
- [ ] 问题生成在 `1200ms` 内完成时，仍等待到最早揭示时间。
- [ ] 问题生成超过 `3000ms` 时，显示“还在整理，可能需要一点时间”。
- [ ] 普通转场仍保持约 `1000ms`，不显示等待文案。
- [ ] 连续点击只发起一次请求、一次路由切换。
- [ ] 引导问题和主题不保存、不发送给 AI。
- [ ] 归档结构和回答页 `commitDraft()` 不变。
- [ ] 当前 Mock 与未来真实本地模型共用同一个 Promise 协调接口。
